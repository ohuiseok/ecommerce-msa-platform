# ADR-008: PENDING 주문 만료 시간과 늦은 결제 성공 처리 정책

## 상태

Accepted

## 배경

현재 주문 생성은 재고를 즉시 차감하고, 쿠폰이 있으면 `UserCoupon`을 `USED`로 변경한 뒤 주문을 `PENDING` 상태로 저장한다. 결제는 별도 API에서 수행되며, 결제 성공 시 주문은 `CONFIRMED`로 전이된다.

사용자가 결제창을 이탈하거나 PG 응답이 지연되면 주문은 `PENDING`으로 남고 재고와 쿠폰이 계속 묶일 수 있다. ADR-004는 즉시 재고 차감 모델을 유지하되 오래된 `PENDING` 주문을 만료 처리하기로 했고, ADR-005는 명시적 결제 실패 주문을 `CANCELLED`로 전이하며 재고와 쿠폰을 복구하기로 했다.

따라서 스케줄러 구현 전에 `PENDING` 주문을 언제 만료할지, 만료 후 늦게 도착한 결제 성공을 자동 확정할지 운영 보정으로 분리할지 결정해야 한다.

## 결정

`PENDING` 주문은 생성 후 30분이 지나도 결제 완료로 확정되지 않으면 만료 대상으로 본다. 만료 대상 주문은 `PENDING -> CANCELLED`로 전이하고 같은 트랜잭션에서 재고와 쿠폰을 복구한다.

| 항목 | 결정 |
| --- | --- |
| 만료 기준 시각 | `orders.created_at` |
| 기본 만료 시간 | 주문 생성 후 30분 |
| 만료 대상 상태 | `PENDING` |
| 만료 후 목표 상태 | `CANCELLED` |
| 자원 복구 범위 | 주문 항목 재고 복구, 사용 쿠폰이 있으면 `USED -> ISSUED` 복구 |
| 늦은 결제 성공 처리 | 자동 확정하지 않고 운영 보정 대상으로 등록 |

## 만료 시간 기준

기본 만료 시간은 30분으로 둔다.

- 일반적인 카드 결제 또는 간편 결제 흐름에서 사용자가 결제창을 완료하기에 충분한 시간을 제공한다.
- 결제 이탈 주문이 재고와 쿠폰을 장시간 점유하는 문제를 제한한다.
- 포트폴리오 단계에서는 PG별 세부 제한 시간보다 단일 정책을 우선 적용해 구현과 운영 기준을 단순하게 유지한다.

향후 실제 PG 연동 시 PG 승인 유효 시간, 가상계좌, 무통장입금처럼 대기 시간이 긴 결제 수단이 추가되면 결제 수단별 만료 시간을 별도 ADR로 분리한다.

## 만료 처리 정책

스케줄러는 현재 시각 기준 `created_at <= now - 30분`인 `PENDING` 주문만 조회한다. 조회 후 실제 취소 직전에도 주문 상태가 여전히 `PENDING`인지 확인해야 한다.

만료 처리는 결제 실패 복구와 같은 원칙을 따른다.

1. 주문을 `PENDING -> CANCELLED`로 전이한다.
2. 상태 전이가 성공한 경우에만 주문 항목 재고를 복구한다.
3. 주문에 사용된 쿠폰이 있으면 쿠폰을 복구한다.
4. 이미 `CANCELLED`, `CONFIRMED` 이상으로 바뀐 주문은 건너뛴다.

재고와 쿠폰 복구는 주문 상태 전이 성공 여부를 기준으로 실행한다. 이렇게 해야 스케줄러가 중복 실행되거나 같은 주문을 여러 번 조회하더라도 재고가 반복 증가하지 않는다.

## 늦은 결제 성공 처리

만료되어 `CANCELLED`가 된 주문에 결제 성공 이벤트가 늦게 도착하면 주문을 자동으로 `CONFIRMED`로 되돌리지 않는다.

| 후보 | 결정 | 이유 |
| --- | --- | --- |
| `CANCELLED -> CONFIRMED` 자동 전이 | 채택하지 않음 | ADR-001에서 `CANCELLED`는 종결 상태다. 이미 복구된 재고와 쿠폰이 다른 주문에 사용됐을 수 있어 자동 확정은 초과 판매와 중복 할인 위험을 만든다. |
| 새 주문 자동 생성 | 채택하지 않음 | 고객 동의, 배송지, 가격, 쿠폰 상태를 다시 확인해야 하므로 자동 생성은 위험하다. |
| 운영 보정 대상으로 등록 | 채택 | 실제 PG 환불 또는 고객 안내가 필요한 상태로 분리해 사람이 확인할 수 있다. 현재 단계의 구현 범위와 가장 잘 맞는다. |

늦은 결제 성공은 Phase 2 Day 7에서 운영 보정 대상으로 등록한다. 실제 PG 환불 API가 붙기 전까지는 자동 환불을 수행하지 않고 보정 목록, 로그, 결제-주문 불일치 조회에서 확인 가능하게 한다.

## 적용 범위

- 만료 스케줄러는 `PENDING` 주문만 대상으로 한다.
- 만료 대상 조회는 `orders.created_at`과 `status` 조건을 사용한다.
- 만료 취소는 사용자 취소와 구분되는 서비스 메서드로 구현한다.
- 만료 취소의 목표 상태는 `CANCELLED`이며, 주문 상태 enum에는 별도 `EXPIRED`를 추가하지 않는다.
- 만료 원인은 현재 단계에서 주문 상태가 아니라 로그와 향후 운영 보정 데이터에 남긴다.
- `CONFIRMED` 이상 주문은 만료 처리 대상에서 제외한다.

## 결과

이 정책은 즉시 재고 차감 모델을 유지하면서 결제 대기 주문이 재고와 쿠폰을 오래 점유하는 문제를 제한한다. 주문 상태 모델은 ADR-001의 단순한 종결 상태 정책을 유지하고, 만료 주문은 `CANCELLED`로 닫는다.

늦은 결제 성공은 자동 상태 변경이 아니라 운영 보정 대상으로 분리한다. 이 결정으로 다음 구현 단계는 오래된 `PENDING` 주문 조회, 상태 전이 기반 idempotent 복구, 보정 대상 등록 흐름에 집중할 수 있다.
