# ADR-005: 결제 실패 주문 상태와 재고·쿠폰 복구 정책

## 상태

Accepted

## 배경

현재 주문 생성은 재고를 즉시 차감하고, 쿠폰이 있으면 주문에 적용한 뒤 `UserCoupon`을 `USED`로 변경한다. 이후 결제 요청은 별도 API에서 수행되며, `MockPgClient`가 실패를 반환하면 결제 row만 `FAILED`로 저장되고 주문은 `PENDING` 상태로 남는다.

이 구조에서는 결제 실패가 확정되어도 재고와 쿠폰이 계속 묶일 수 있다. 단순히 재고와 쿠폰만 복구하면 아직 살아 있는 `PENDING` 주문이 같은 자원을 다시 참조하는 모순이 생기므로, 결제 실패 시 주문의 목표 상태와 복구 트랜잭션 범위를 먼저 정해야 한다.

## 결정

결제 실패가 명확히 확정된 주문은 `CANCELLED`로 전이한다. `PAYMENT_FAILED` 상태는 현재 단계에서 추가하지 않는다.

| 후보 | 결정 | 이유 |
| --- | --- | --- |
| `PAYMENT_FAILED` 주문 상태 추가 | 채택하지 않음 | 실패 사유를 주문 상태로 명확히 표현할 수 있지만, 상태 enum, 조회 API, 상태 전이표, 기존 테스트 영향이 크다. 현재 목표인 묶인 자원 복구에는 별도 상태가 필수는 아니다. |
| `CANCELLED`로 전이 | 채택 | ADR-001의 기존 종결 상태를 재사용해 실패 주문이 더 진행되지 않도록 막고, 재고·쿠폰 복구와 함께 가장 작은 변경으로 일관성을 회복할 수 있다. |
| 주문은 `PENDING` 유지 후 자원만 복구 | 채택하지 않음 | 복구된 재고와 쿠폰을 참조하는 미결 주문이 남아 이후 결제 재시도, 만료 처리, 운영 조회에서 모순을 만든다. |

## 실패 판단 범위

- PG 또는 Mock PG가 동기 응답으로 명시적인 실패를 반환한 경우만 이 정책의 대상이다.
- 서버 타임아웃, 네트워크 단절, PG 응답 불명처럼 성공 여부를 모르는 경우는 실패로 단정하지 않는다.
- 응답 불명 상태와 늦게 도착한 결제 성공 이벤트는 ADR-008의 `PENDING` 만료 정책과 Phase 2 웹훅 보정 흐름에서 별도로 다룬다.

## 복구 정책

결제 실패 처리에서는 하나의 로컬 트랜잭션 안에서 아래 작업을 함께 수행한다.

1. 결제 row를 `FAILED`로 저장한다.
2. 주문을 `PENDING -> CANCELLED`로 전이한다.
3. 주문 항목의 재고를 복구한다.
4. 주문에 사용된 쿠폰이 있으면 `USED -> ISSUED`로 복구한다.

주문이 이미 `CANCELLED`이면 같은 실패 복구 요청은 추가 재고 증가나 쿠폰 중복 복구 없이 완료되어야 한다. 이를 위해 구현은 주문 상태 전이를 복구 실행 여부의 기준으로 삼고, 실제 재고·쿠폰 복구는 `PENDING -> CANCELLED` 전이가 성공한 경우에만 수행한다.

## 결제 재시도 정책

- 같은 `orderId + idempotencyKey` 재요청은 ADR-002에 따라 기존 실패 결제 row를 반환한다.
- 실패 복구로 주문이 `CANCELLED`가 된 뒤에는 같은 주문에 새 `idempotencyKey`로 결제를 다시 시도할 수 없다.
- 사용자가 결제를 다시 시도하려면 새 주문을 생성해야 한다. 이때 복구된 재고와 쿠폰을 다시 사용할 수 있다.

## 적용 범위

- `PaymentService.requestPayment`는 PG 실패가 확정되면 결제 실패 저장과 주문 취소 복구를 같은 트랜잭션 안에서 호출한다.
- `OrderService`는 결제 실패 복구용 메서드를 별도로 제공한다. 사용자 취소와 구분하되 목표 상태는 `CANCELLED`로 동일하게 둔다.
- 결제 실패 복구 메서드는 `PENDING` 주문만 취소하고 자원을 복구한다.
- 이미 `CONFIRMED` 이상으로 진행된 주문에 실패 결제가 뒤늦게 연결되는 경우는 자동 복구하지 않고 결제-주문 불일치 조회 또는 운영 보정 대상으로 남긴다.
- 실패 사유는 주문 상태가 아니라 결제 row의 `failureReason`과 로그 필드에 남긴다.

## 결과

결제 실패가 확정된 주문은 즉시 종결 상태로 이동하고, 같은 트랜잭션에서 재고와 쿠폰을 되돌린다. 이 결정은 주문 상태 모델을 단순하게 유지하면서도 결제 실패 후 자원이 묶이는 문제를 줄인다.

향후 실패 주문을 사용자 화면이나 운영 화면에서 별도 상태로 구분해야 하는 요구가 커지면 `PAYMENT_FAILED` 상태 추가를 다시 검토한다. 현재 단계에서는 결제 실패의 상세 의미를 `payments` 데이터와 로그에 두고, 주문은 진행 가능 여부를 나타내는 상태로 유지한다.
