# ADR-004: 즉시 재고 차감 유지와 TTL 예약 재고 도입 조건

## 상태

Accepted

## 배경

현재 주문 생성은 `ProductRepository.decreaseStockIfAvailable`의 조건부 `UPDATE`로 상품 재고를 즉시 차감한다. 같은 트랜잭션 안에서 주문 생성, 쿠폰 사용, 재고 차감이 함께 처리되므로 구현이 단순하고 재고 초과 판매를 DB 업데이트 조건으로 방어할 수 있다.

다만 결제는 주문 생성 이후 별도 API에서 수행된다. 사용자가 결제창을 이탈하거나 PG 실패, 응답 지연, 서버 장애가 발생하면 주문은 `PENDING`으로 남고 재고와 쿠폰이 묶일 수 있다. TTL 기반 예약 재고는 이런 묶임을 시간 기준으로 복구하기 쉽지만, 예약 상태와 만료 처리를 별도로 운영해야 한다.

## 결정

현재 단계에서는 즉시 재고 차감 방식을 유지한다. Phase 2에서는 즉시 차감 모델 위에 `PENDING` 주문 만료 기준과 재고·쿠폰 복구 스케줄러를 추가해 묶인 자원을 회수한다.

TTL 예약 재고는 바로 도입하지 않는다. 대신 아래 조건 중 하나가 실제 운영 요구 또는 테스트 결과로 확인되면 별도 ADR에서 예약 재고 모델로 전환을 검토한다.

| 조건 | 전환 검토 이유 |
| --- | --- |
| 결제 이탈 또는 실패로 오래 묶인 재고가 판매 가능 재고를 의미 있게 왜곡한다. | 즉시 차감은 주문 생성 시점에 판매 가능 수량을 줄이므로 결제 미완료 주문이 많으면 품절처럼 보일 수 있다. |
| 결제 대기 시간이 길고 늦은 PG 성공 이벤트를 정상 주문으로 받아야 한다. | 단순 만료 취소는 늦은 성공 이벤트와 충돌할 수 있어 예약 상태와 확정 상태를 분리하는 편이 명확하다. |
| 주문 생성과 결제 승인을 하나의 사용자 흐름으로 강하게 묶어야 한다. | 예약 재고는 결제 성공 시 확정 차감으로 전환하는 모델을 만들기 쉽다. |
| 판매 이벤트처럼 짧은 시간에 대량 주문이 몰리고 대기 주문 만료가 자주 발생한다. | 예약 만료 처리를 독립 모델로 두면 만료 정책과 모니터링을 더 세밀하게 조정할 수 있다. |

## 비교

| 항목 | 즉시 재고 차감 | TTL 예약 재고 |
| --- | --- | --- |
| 구현 복잡도 | 낮음. 현재 코드와 트랜잭션 경계를 유지한다. | 높음. 예약 테이블, 만료 시간, 확정 전환, 중복 복구 방어가 필요하다. |
| 초과 판매 방어 | 조건부 `UPDATE`로 현재 요구를 만족한다. | 예약 생성도 조건부 차감 또는 가용 수량 계산을 원자적으로 처리해야 한다. |
| 결제 실패 복구 | 주문 취소 또는 만료 처리에서 재고를 되돌려야 한다. | 예약 만료로 판매 가능 재고를 회복하는 모델을 명확히 둘 수 있다. |
| 늦은 결제 성공 처리 | 만료 후 성공 이벤트는 운영 보정 또는 환불 대상으로 분리해야 한다. | 예약이 살아 있으면 확정, 만료 후 성공이면 보정 대상으로 나누기 쉽다. |
| 운영 가시성 | `PENDING` 주문과 차감된 재고를 함께 봐야 한다. | 예약 수량, 만료 예정 수량, 확정 수량을 분리해서 볼 수 있다. |

## 적용 정책

- 주문 생성 시 재고는 계속 즉시 차감한다.
- 결제 실패가 확정된 주문은 ADR-005에서 정한 상태로 전이하고 같은 트랜잭션에서 재고와 쿠폰을 복구한다.
- 오래된 `PENDING` 주문은 ADR-008에서 정한 만료 시간 이후 스케줄러가 취소 또는 실패 상태로 전이하고 재고와 쿠폰을 복구한다.
- 재고 복구는 중복 실행되어도 재고가 반복 증가하지 않도록 주문 상태 전이와 함께 idempotent하게 구현한다.
- 늦게 도착한 결제 성공 이벤트는 자동 확정보다 운영 보정 대상으로 우선 등록한다.

## 결과

즉시 재고 차감 모델을 유지해 현재 코드의 단순성과 조건부 업데이트 기반 동시성 방어를 살린다. Phase 2의 복구 작업은 예약 재고를 새로 만들지 않고 `PENDING` 주문 만료와 실패 복구를 먼저 보강한다.

TTL 예약 재고는 포기한 선택지가 아니라 전환 조건이 충족될 때 다시 검토할 확장안으로 남긴다. 이 결정으로 다음 구현 단계는 결제 실패 주문 상태, `PENDING` 만료 기준, 복구 스케줄러에 집중한다.
