# ADR-003: traceId와 도메인 로그 필드 정책

## 상태

Accepted

## 배경

주문, 결제, 쿠폰 흐름은 하나의 사용자 요청 안에서 여러 도메인 서비스를 연쇄 호출한다. 장애 분석 시 주문 ID나 결제 ID만으로는 HTTP 요청 단위의 전체 흐름을 묶어 보기 어렵고, 로그 메시지마다 필드명이 달라 검색 기준도 흔들릴 수 있다.

## 결정

모든 HTTP 요청은 `X-Trace-Id` 헤더를 기준으로 traceId를 결정한다. 클라이언트가 값을 보내면 앞뒤 공백을 제거해 사용하고, 없으면 서버가 UUID를 생성한다. 서버는 같은 값을 응답 `X-Trace-Id` 헤더로 돌려준다.

traceId는 요청 처리 동안 SLF4J MDC의 `traceId` 키에 저장하고, 로그 레벨 패턴에 `traceId=%X{traceId:-}`를 포함한다. 요청이 끝나면 MDC 값을 제거해 스레드 재사용으로 인한 오염을 막는다.

## 로그 필드

주문, 결제, 쿠폰 로그는 메시지 앞에 `event=<domain.action>`을 두고, 가능한 경우 아래 필드를 같은 이름으로 기록한다.

| 필드 | 의미 |
| --- | --- |
| `orderId` | 주문 식별자 |
| `paymentId` | 결제 식별자 |
| `userId` | 사용자 식별자 |
| `couponId` | 쿠폰 마스터 식별자 |
| `userCouponId` | 사용자 발급 쿠폰 식별자 |
| `couponCode` | 운영 식별용 쿠폰 코드 |
| `amount`, `totalAmount` | 결제 또는 주문 금액 |
| `status` | 상태 변경 또는 멱등 재요청 결과 상태 |
| `reason` | 실패 사유 |

## 개인정보와 제한

로그에는 이메일, 전화번호, 배송지, 카드번호를 남기지 않는다. traceId는 외부 시스템과 함께 쓰이는 상관관계 ID로만 사용하고, 사용자 식별 정보로 해석하지 않는다.

클라이언트가 지나치게 긴 `X-Trace-Id`를 보내면 최대 64자로 제한한다. 더 엄격한 허용 문자 정책이나 W3C Trace Context 도입은 분산 추적 시스템을 붙이는 단계에서 다시 결정한다.

## 결과

운영자는 traceId로 단일 요청의 전체 흐름을 검색하고, `event`, `orderId`, `paymentId`, `userId` 같은 일관된 필드로 주문·결제·쿠폰 이벤트를 추적할 수 있다. 별도 tracing backend 없이도 현재 로그 기반 장애 분석 품질을 높인다.
